Personal Recommender 設計レビュー

YouTube の推薦に依存せず、自分が管理する評価履歴からフィードを組み立てる個人向けシステム。

正: personal-recommender-v2.ja.md ／ implementation-notes.ja.md
このページはレビュー用のレイアウトで、内容は上記 2 本と同じ。

1. 何を作ったか

3 つの場所に責務を分け、GPU をリクエスト経路から外した構成。

Cloudflare   どんな動画があるか、自分が何を評価したかを知っている。常時稼働
Runpod       ある動画を自分が何点と付けそうかを予測する。それ以外は寝ている
YouTube      動画を持っている

Cloudflare は起きたままでもコストがかからず、GPU は暖まっている分だけ課金される。だから リクエストに答える必要があるものはすべて Cloudflare に置き、GPU は後回しにできる仕事 ——学習と事前スコアリング——のためだけに起こす。

最重要の帰結

フィード生成中に GPU を呼ばない（設計書 §33）

フィードは事前に計算されたスコアを読むだけ。Runpod が落ちていても、寝ていても、 まだ一度も設定されていなくても、アプリは動く。学習が止まるだけ（§49）。

3. スコアリング

モデル呼び出しではなく式。同じ入力に同じ答えを返し、実行コストがゼロで、全項目を言葉で説明できる。

final_score = 0.65 × preference_score      ← GPU が事前生成する唯一の項
            + subscription_bonus
            + freshness_bonus
            + explicit_interest_bonus
            + exploration_bonus
            − seen_penalty
            − muted_interest_penalty

各項は個別に保持され、そのまま「なぜこれが出たか」パネルの材料になる（§39）。LLM は使わない。

Subscription

登録チャンネルの新着。最優先。1 チャンネル 1 クォータ単位

Related

モデルが採点済みの領域。自信を持って語れる範囲

Explore

モデルが何も知らない領域。予測値なし

50 件フィードなら 25 / 15 / 10。レーンごとに別プールから選ぶので、 「Anagnorisis が予測しやすい動画だけがフィードを占領する」ことが起きない（§34）。

4. 設計書が触れていなかったので決めたこと

決定

学習は「現在の評価」で行う

§11 はイベントを消さないと定め、同時に最新評価を現在値とすると書いている。学習には現在値だけを使う。

全イベントを渡すと、ユーザーがすでに置き換えた評価をモデルが学ぶ。 ログには両方残るので、興味の変化を分析するという §11 の目的は損なわれない。

決定

学習ジョブの冪等キーにモデル版番号を含めない

モデル版は出力の名前であって入力ではない。

含めると 1 回目で版番号が繰り上がるため 2 回目のハッシュが必ず変わり、 「評価が増えていないのに再学習を押した」というまさに検出したいケースを一度も検出できない。

決定

未採点の動画には候補プールの平均を与える

固定値 5.0 ではなく、そのプールで実際に採点された動画の平均。

評価が全体に辛いか甘いかで、固定値はプール全体の上にも下にも来る。上なら未採点が フィードを占領し、下なら永久に出てこない。

決定

impressions を rating_events と分ける

§33 の seen_penalty の材料。設計書にテーブルの記載がない。

「表示した」と「評価した」は別の事実。同じテーブルに寄せると、 スクロールで通り過ぎただけの動画が「見たくない」という宣言と区別できなくなる。

他に oauth_tokens / oauth_states / api_quota_usage / settings を追加。いずれも §16・§42・§38・§45 が要求する動作にテーブルが割り当てられていなかったもの。

5. 設計書どおりにできなかったこと

乖離

Network Volume のレイアウト（§27）

設計書は project_config/ と並べて trained/ と cache/ を置く。 Anagnorisis は両方を project_config_path から導出するため、実装では内側に入る。

上流の設定解決に手を入れれば設計書どおりにできるが、それは §51 が 「本体を改造しすぎない」として避けよと言っている行為そのもの。

乖離

Runpod のリクエスト形式（§22 と §23 が食い違う）

§22 の入れ子形（input.payload）を正とした。操作を増やしても形が変わらないため。 GPU 側のパーサは §23 の平坦形も受け付ける。
