# 実装ノート

`personal-recommender-v2.ja.md` を実装した際に、設計書が定めていなかった点、および設計書の記述どおりにはできなかった点の記録。

設計書を読んだだけではコードの形が説明できない箇所だけを挙げる。設計書に書いてあるとおりに実装した部分はここには出てこない。

---

## 1. 設計書が触れていなかったので決めたこと

### 1.1 タイムスタンプの単位

設計書 §9〜§15 のスキーマはすべて `INTEGER` なので、D1 の列と TypeScript のドメイン型の両方を **エポックミリ秒** に統一した。ISO 8601 文字列は、人間が読むところ（`ratings.jsonl` などのエクスポート）だけで使う。

境界ごとに変換すると、どちらの単位でいるのかがファイルごとに変わる。

### 1.2 設計書にスキーマがなかったテーブル

| テーブル | 追加した理由 |
|---|---|
| `oauth_tokens` | §16 が「AES-GCM で暗号化して D1 に置く」と定めているのに、置き場所のスキーマがない |
| `oauth_states` | OAuth の `state` をサーバ側で保持し、偽装されたコールバックを受け付けないため |
| `api_quota_usage` | §42 の `search.list` 予算は、呼ぶ**前**に残量を数えないと機能しない |
| `impressions` | §33 の `seen_penalty` の材料。`rating_events` から導くことはできない（下記 1.3） |
| `settings` | §38 の Discovery スライダーと §45 の `settings.json` エクスポートに必要 |

### 1.3 `seen_penalty` を `rating_events` から作らない

「表示した」と「評価した」は別の事実であり、同じテーブルに寄せると、無視されたインプレッションと意図的な評価 0 が区別できなくなる。区別できないと、スクロールで通り過ぎただけの動画が「見たくない」と宣言されたことになってしまう。よって `impressions` を別に持つ。

インプレッションは、フィードを組み立てた時点で記録する。ビューポートに入った時点ではない。`seen_penalty` が答えたい問いは「同じ動画を毎日出していないか」であり、それには「フィードに載ったか」で足りる。スクロール精度の答えを得るためにブラウザから逐次報告させる価値はない。

### 1.4 学習は「現在の評価」で行う

設計書 §11 は過去のイベントを消さないと定め、同時に「最新評価を現在値として扱う」と書いている。学習データはこの**現在値**だけを使う。

イベントを全部渡すと、ユーザーがすでに置き換えた評価をモデルが学ぶことになる。ログには両方残るので、興味の変化を後から分析するという §11 の目的は損なわれない。

### 1.5 学習ジョブの `payload_hash` にモデル版番号を含めない

§47 の冪等キーは「プロファイル + モデル版 + 入力 ID」と書かれているが、学習に限ってはモデル版を除いた。

モデル版は**出力の名前**であって入力ではない。含めると、1 回目の送信で版番号が繰り上がるため 2 回目のハッシュが必ず変わり、「評価が増えていないのに再学習を押した」というまさに検出したいケースを一度も検出できない。スコアリングでは、どの版で採点したかが結果の意味を変えるので含めている。

### 1.6 スコア未生成の動画に与える予測値

`preference_score` がない動画には、**候補プール内で実際に採点された動画の平均**を与える。固定値 5.0 ではない。

ユーザーの評価が全体に辛いか甘いかによって、固定の 5.0 はプール全体の上にも下にも来る。上に来れば未採点の動画がフィードを占領し、下に来れば永久に出てこない。プール平均なら「未知」が「このプールでの平均並み」を意味し、これが唯一正直な読み方になる。

### 1.7 related レーンと explore レーンの分け方

§34 は3レーンを要求するが、related と explore の境界は定めていない。実装では**現行モデルが採点済みかどうか**で分けた。

- related — 予測値がある。モデルが自信を持って語れる領域
- explore — 予測値がない。モデルが何も知らない領域

「Anagnorisis が予測しやすい動画だけがフィード全体を占領するのを防ぐ」という §34 の目的に、この分け方が直接対応する。

### 1.8 学習に必要な最小評価数は 10 件

数件で学習したモデルはノイズを返すが、GPU 時間は同じだけ請求される。10 件は一度の視聴で到達できる数であり、かつ結果を使う気になる下限。

### 1.9 興味コントロールの照合範囲

タイトル・タグ・チャンネル名に対する部分一致。説明文は除外した。

説明文はリンクとスポンサー文で埋まっており、そこで一致させると「Firefox 関連なのでおすすめ」という自信ありげで実際には外れた推薦理由が出る。V1 で embedding を使わないのは §53 の判断どおりで、ランキング経路にモデル呼び出しを戻さないためでもある。

### 1.10 クォータ台帳の日付は JST

`search.list` の実際のリセットは太平洋時間の深夜だが、台帳は JST の暦日で数える。1 日の予算を許容量の 3 分の 1（30/100）に抑えてあるため、暦のずれで超過することはない。画面に出る数字は、使う人が生きている暦に合っている方がよい。

## 2. 設計書どおりにできなかったこと

### 2.1 Runpod のリクエスト形式（§22 と §23）

§22 は `{"input": {"operation": ..., "payload": {...}}}`、§23 は各フィールドを `input` 直下に置いている。実装は **§22 の入れ子形を正**とした。操作を増やしても形が変わらないのはこちらだけであるため。

ただし GPU 側のパーサは両方を受け付ける。ジョブログからコピーしたペイロードがそのまま動く方が、片方だけ正しいドキュメントより役に立つ。

### 2.2 Network Volume のレイアウト（§27）

設計書は `project_config/` と並べて `trained/` と `cache/` を置いている。Anagnorisis は両方を `project_config_path` から導出する（`<project_config>/models` と `<project_config>/cache`）ため、実装では `project_config/` の**内側**に入る。

```text
/runpod-volume/
├── models/                         共有の埋め込みモデル重み
└── project_config/
    └── <profile>/
        ├── memory/                 評価のメモリファイル（D1 からの派生）
        ├── models/
        │   ├── universal_evaluator.pt   現在有効な版
        │   └── versions/model-N.pt      保存された各版
        └── cache/
```

上流の設定解決に手を入れれば設計書どおりの形にできるが、それは §51 が「Anagnorisis 本体を改造しすぎない」として避けよと言っている行為そのものになる。

### 2.3 メモリファイルは学習のたびに作り直す

Anagnorisis は評価をメモリファイル（`memory/<日付>/<hash>.md`）として持ち、そこから学習する。実装では、学習のたびにこのフォルダを空にしてから書き直す。

正本は §4.1 のとおり D1 の `rating_events` であり、メモリファイルはその派生キャッシュにすぎない。前回分を残すと、ユーザーがすでに置き換えた評価が学習データに二重に入る。

書き込み時には元の評価日時を `when` として渡すので、同じ評価は毎回同じファイルに落ちる。

### 2.4 モデル版の切り替え方

§48 の atomic switch は、`model-15.tmp` を書いて成功したら `model-15` にリネームする、として実装した。加えて、Anagnorisis は評価器を固定ファイル名 `universal_evaluator.pt` から読むため、「版を選ぶ」ことは「その版のバイト列をそこに置く」ことになる。こちらも一時名に書いてからリネームする。

これが安全なのは §26 の `workersMax = 1` が前提。ワーカーが 2 つあれば、一方が採点している最中に他方が別の版を有効化しうる。

## 4. 前バージョンからの移行

旧設計（`personal-preference-model-youtube-recommender-v1.en.md`）はブラウザ拡張に嗜好データを閉じ込める構成だった。今回の変更で拡張（`packages/extension`）とローカル推薦モデル（`packages/core`）は削除した。

D1 は作り直していない。旧 `catalog_item` のクロール済みメタデータは `migrations/0002` で `channels` と `videos` に移送してから、テーブルを落とす。クォータを使って集めたデータであり、捨てる理由がない。

`migrations/0001_catalog.sql` はファイル名を変えずに残してある。適用済み記録と名前が一致していないと、wrangler が再適用を試みるため。

## 6. ターン数

| | |
|---|---|
| 予定ターン数 | 4（設計提示 → 承認 → 実装 → 報告） |
| 実際のターン数 | 5（設計提示、確認質問2回、実装、報告） |

差分は、拡張の扱い・推薦エンジンの置換範囲・実装フェーズ・ディレクトリ構成という 4 つの決定と、拡張のローカルデータの扱いおよび upstream 参照の可否を、実装前に確定させたため。いずれも後から変えると手戻りが大きい判断だったので、確認に使ったターンは回収できている。
